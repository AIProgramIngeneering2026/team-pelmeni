# ADR-0002. Восстановление жизненного цикла брони из БД

- Дата: 13.11.2026.
- Статус: Принято.

## Контекст и ограничения

В проекте Job означает бронь: `PENDING_CONFIRMATION`, `CONFIRMED`, `CANCELLED`, `COMPLETED`. Состояния `running` у брони нет. [Архитектура](../architecture.md) из PR №17 предусматривает Storage, Registry и Scheduler; [контракт Tool](../tool-contract.md#confirmbookingtool-и-scheduler) из PR №18 требует автоматических переходов по времени независимо от задержки Scheduler.

Процесс может остановиться до начала или окончания встречи и запуститься после обоих событий. Таймеры только в памяти потеряют эти переходы. Восстановление не должно создавать новую бронь, воскрешать терминальную или повторять SMS автоматически.

## Решение

Хранить бронь и расписание связанных заданий в постоянной БД. Scheduler после перезапуска восстанавливает необходимые переходы из сохранённых статусов и времени, а не из памяти остановленного процесса.

1. До готовности сервиса к пользовательским операциям выполнить восстановительный проход. При недоступной БД `/health` возвращает `503 SERVICE_UNAVAILABLE`; переходы не считаются восстановленными.
2. Для `PENDING_CONFIRMATION` с `start_at <= now` выполнить переход в `CANCELLED`. Даже если прошло также время окончания, такая бронь не становится `COMPLETED`: её не подтвердили.
3. Для `CONFIRMED` с `end_at <= now` выполнить переход в `COMPLETED`. Если начало уже наступило, а конец ещё нет, оставить `CONFIRMED`.
4. Остальные будущие брони сохранить в прежнем статусе. `CANCELLED` и `COMPLETED` не изменять. Идентификаторы и данные броней сохраняются.
5. Переход выполнять атомарным условным обновлением текущего статуса в транзакции. Повторный проход и конкуренция с подтверждением, отменой или переносом не должны повторно применять переход либо использовать устаревшее расписание. При конкуренции перечитать запись и проверить правила заново.
6. В обычной работе Scheduler проверяет просроченные переходы не реже одного раза в секунду при доступной БД. Перед чтением или изменением конкретной брони система также актуализирует её состояние по времени. Ответ не зависит от того, успел ли сработать фоновый проход.
7. Для сравнения использовать один источник текущего времени — БД, с приведением дат к UTC. Перенос брони и изменение её расписания фиксировать атомарно.
8. Не проигрывать при старте все прежние бизнес-команды и не повторять автоматически попытки SMS с неизвестным результатом; обработка таких попыток определена в [ADR-0003](0003-sms-without-automatic-retry.md).

Фиксация успешной брони и ключа при потере HTTP-ответа регулируется [ADR-0001](0001-persistent-idempotency.md). Клиент после восстановления получает актуальные состояния через `GET /bookings`. Нового HTTP-ответа на уже оборвавшееся соединение нет.

## Рассмотренные альтернативы

| Альтернатива | Почему не выбрана |
|---|---|
| Только таймеры в памяти | После остановки процесса теряются. |
| Отменить при старте все активные брони | Отменяет действительные подтверждённые встречи. |
| Внешняя очередь и отдельный сервис расписания | Усложняет учебный проект; всё равно требует идемпотентных переходов и согласования с БД. |
| Актуализация только при обращении клиента | Не обеспечивает фоновые переходы для броней, к которым никто не обращается. |

## Цена решения

Нужны индексы по статусу и времени, восстановительный проход, условные обновления и согласование расписания с переносом. Восстановление увеличивает время старта; сервис зависит от доступности БД. Во время остановки фоновые действия не выполняются, после запуска состояние догоняет время.

## Условия пересмотра

Пересмотреть при недопустимом времени старта, росте числа броней, переходе к нескольким Scheduler или появлении строгого SLA на выполнение фоновых действий. Для нескольких экземпляров потребуется проверить координацию всех побочных эффектов, а не только обновления статусов.
