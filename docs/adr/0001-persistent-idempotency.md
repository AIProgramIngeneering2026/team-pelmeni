# ADR-0001. Постоянный ключ идемпотентности создания брони

- Дата: 13.11.2026.
- Статус: Принято.

## Контекст и ограничения

Сотрудник может дважды нажать кнопку создания или повторить запрос после потери HTTP-ответа. Проверка пересечений сама по себе вернёт конфликт вместо результата первого запроса. Нужен способ отличить повтор от новой операции.

В [OpenAPI](../api/openapi.yaml) и [CreateBookingTool](../tool-contract.md#createbookingtool) уже предложены обязательный `Idempotency-Key`, область «пользователь + операция», ответы `201`, `200`, `409` и атомарное сохранение ключа с бронью. Материалы находятся в PR №18; это не подтверждение реализации.

## Решение

Использовать постоянную запись идемпотентности в той же БД, что и бронь. Решение применяется к `POST /bookings`.

1. Ключ записи — `(actor_id, operation, Idempotency-Key)`. Уникальность обеспечивается БД. Одновременные запросы с одним ключом не могут создать две брони.
2. Сохранять нормализованные параметры и первоначальный успешный результат. Порядок полей JSON не влияет на сравнение; даты сравниваются как моменты времени, как указано в OpenAPI.
3. Создание брони, связанных записей фоновых заданий и успешной записи идемпотентности фиксировать одной транзакцией. SMS не включать в транзакцию БД.
4. Первое успешное создание возвращает `201` и `Booking`. Повтор с теми же параметрами — `200` с сохранённым результатом и прежним `id`, без нового Tool и нового уведомления. Повтор с другими параметрами — `409 IDEMPOTENCY_KEY_REUSED`; `details.field = header.Idempotency-Key`.
5. Пока первый запрос ещё выполняется, повтор возвращает `409 REQUEST_IN_PROGRESS` с тем же указанием поля. Сервис не обязан ждать завершения первого запроса.
6. После сбоя до commit транзакция откатывается, повтор может выполнить создание. После commit повтор читает сохранённый результат. Незавершённость запроса не должна оставлять постоянную блокировку ключа после перезапуска.
7. Успешные записи не удалять по TTL в рамках текущего контракта. Неуспешная операция без commit не резервирует ключ навсегда. Аутентификация выполняется до поиска ключа; чужая запись по ключу не возвращается.

Сохранённый результат — снимок создания. Если бронь позднее подтверждена, отменена или перенесена, повтор создания всё равно возвращает этот снимок. Текущее состояние пользователь получает через `GET /bookings` среди своих броней. Новое бронирование требует нового ключа; прежняя бронь не изменяется.

## Рассмотренные альтернативы

| Альтернатива | Почему не выбрана |
|---|---|
| Блокировка кнопки только на клиенте | Не защищает от сетевого повтора, нескольких вкладок и другого клиента. |
| Только проверка пересечений | Не позволяет восстановить успешный ответ и отличить повтор от другой брони. |
| Кэш ключей в памяти | Теряет защиту при перезапуске и не согласуется между экземплярами. |
| Ключ с TTL | После истечения срока тот же запрос может создать новую бронь; срок пришлось бы включить в API-контракт. |

## Цена решения

Дополнительная таблица, уникальный индекс, транзакционная координация и хранение снимка ответа. Объём данных растёт без TTL. Клиент должен сохранять ключ и исходные параметры до получения однозначного результата. Снимок ответа может отличаться от актуального состояния брони, поэтому интерфейс должен обновлять список броней.

## Условия пересмотра

Пересмотреть при значительном росте хранилища, введении срока хранения персональных данных, изменении схемы ответа или добавлении нескольких независимых хранилищ. TTL допустим только после явного определения окна идемпотентности и поведения за его пределами в OpenAPI.
