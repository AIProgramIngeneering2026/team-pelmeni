# ADR-0003. Доставка SMS без автоматических повторов

- Дата: 13.11.2026.
- Статус: Принято.

## Контекст и ограничения

[Требования первой практики](../requirements.md#предложение-3-дубль-уведомления-при-повторе) сознательно исключают автоматические повторы SMS и допускают ручной повтор администратором. [RetryNotificationTool](../tool-contract.md#retrynotificationtool) и `POST /notifications/{id}/retry` в [OpenAPI](../api/openapi.yaml) из PR №18 предусматривают `502`, `504` и независимость состояния брони от ошибки SMS.

При тайм-ауте неизвестно, успел ли провайдер принять сообщение. Без договорённости о дедупликации у провайдера обещать однократную доставку нельзя. В текущем контракте не задано численное значение тайм-аута.

## Решение

Сохранить модель одной автоматической попытки доставки, отделённой от успешного изменения брони. Не выполнять автоматический повтор неуспешной или неопределённой попытки.

1. Бронь и запись уведомления сохраняются до обращения к SMS-провайдеру. После commit ошибка SMS не откатывает создание, отмену или перенос брони.
2. Для одного обращения SmsNotifier установить общий предельный срок ожидания **5 секунд**, включая соединение и чтение ответа. Невалидный JSON, отсутствие обязательного поля, переименование ожидаемого поля или отказ провайдера считаются ошибкой адаптера.
3. Фиксировать попытку до сетевого вызова и её результат после вызова. Принятый и проверенный ответ — `SENT`; однозначный отказ или неправильный ответ — `FAILED`; тайм-аут либо перезапуск во время вызова — `UNKNOWN`. Это внутренние статусы доставки, не новые состояния брони.
4. Для синхронного ручного повтора администратор получает `200 NotificationAttempt` при принятии сообщения, `502 NOTIFICATION_PROVIDER_ERROR` при отказе или неправильном ответе и `504 NOTIFICATION_TIMEOUT` при истечении срока ожидания. Ошибки используют схему `Error` из OpenAPI; `details.field = null`.
5. При первоначальной фоновой отправке нового HTTP-ответа клиенту нет: запрос бронирования уже завершился. Состояние брони остаётся результатом бизнес-операции; сбой и неопределённый результат доставки сохраняются и доступны в эксплуатационных логах. Отдельный API просмотра статуса доставки текущим контрактом не предусмотрен.
6. После перезапуска не запускать повторно попытку, которая была начата, но не имеет зафиксированного результата: отметить её `UNKNOWN`. Сохранённое уведомление, для которого ещё не начиналась ни одна попытка, может получить первую попытку.
7. Ручной повтор `FAILED` или `UNKNOWN` создаёт новую попытку. Для `SENT` и при уже выполняющейся попытке возвращать `409 INVALID_STATE` с `details.field = path.id`. Одновременные ручные повторы одной записи сериализуются в БД.
8. Для `UNKNOWN` администратор до повтора проверяет состояние у провайдера, если это возможно. **Риск повторного SMS сознательно принимается**: ручной повтор после потерянного ответа не гарантирует отсутствия дубля. Восстановление сервером подтверждённой доставки без подтверждения провайдера не допускается.

## Рассмотренные альтернативы

| Альтернатива | Почему не выбрана |
|---|---|
| Бесконечный или ограниченный автоматический retry | Противоречит согласованным требованиям первой практики и может дублировать SMS. |
| Откатить бронь при ошибке SMS | Недоступность уведомлений начнёт отменять успешные бизнес-операции; отправленное SMS всё равно нельзя откатить. |
| Exactly-once через ключ у провайдера | Нужен подтверждённый контракт провайдера с дедупликацией; в материалах проекта его нет. |
| Не ограничивать ожидание | Зависший провайдер удерживает ресурсы приложения неопределённое время. |

## Цена решения

Часть SMS не будет доставлена без вмешательства администратора. Требуются постоянные записи попыток, блокировка параллельного повтора и диагностика неопределённых исходов. Статус брони не подтверждает доставку SMS. Тайм-аут 5 секунд может отклонять медленные, но работоспособные ответы.

## Условия пересмотра

Пересмотреть при появлении у провайдера идемпотентного API, подтверждений доставки, согласованного SLA или обязательной гарантии напоминаний. Автоматический retry вводить только после изменения требований и описания дедупликации, лимита попыток и обработки неопределённого результата.
