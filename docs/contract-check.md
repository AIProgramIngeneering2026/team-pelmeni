# Проверка контракта колодой К1–К10

Дата: 13.11.2026.

Job — бронь с состояниями `PENDING_CONFIRMATION`, `CONFIRMED`, `CANCELLED`, `COMPLETED`. Проверка основана на контрактах из PR №17 и №18 и принятых ADR-0001–0004.

| Карта | Ответ контракта |
|---|---|
| **К1 Двойной клик** | Для двух `POST /bookings` одного сотрудника с одинаковыми параметрами и `Idempotency-Key` создаётся одна бронь: первый успех — `201 Booking`, завершённый повтор — `200` со снимком первого результата и прежним `id`; пока первый запрос выполняется — `409 REQUEST_IN_PROGRESS`. Другие параметры с тем же ключом — `409 IDEMPOTENCY_KEY_REUSED`. Два разных ключа не являются повтором; пересекающиеся брони дают `409 BOOKING_CONFLICT`. Источники: [OpenAPI](api/openapi.yaml), `info.description`, `paths./bookings.post`; [CreateBookingTool](tool-contract.md#createbookingtool); [ADR-0001](adr/0001-persistent-idempotency.md#решение). |
| **К2 Ответ потерялся** | Клиент сохраняет исходный ключ и параметры и повторяет `POST /bookings`: после commit получает `200` с первоначальным `id`, до commit после отката запрос может создать бронь с `201`, при ещё работающем первом запросе — `409 REQUEST_IN_PROGRESS`. Создание и успешная запись ключа атомарны, поэтому commit без сохранённого ключа не допускается. Текущее состояние доступно в `GET /bookings`; отдельного поиска по ключу нет. Источники: [OpenAPI](api/openapi.yaml), `info.description`, `paths./bookings`; [ADR-0001](adr/0001-persistent-idempotency.md#решение). |
| **К3 Неизвестная операция** | Произвольный выбор операции в теле `POST /bookings` не поддерживается: `BookingInput.additionalProperties = false`, поле `operation` недопустимо — `422` со схемой `Error` и ошибочным полем в `details`, бронь не создаётся. При внутреннем вызове неизвестной операции Dispatcher — `422 UNKNOWN_OPERATION`, поле `operation`, без создания брони. Карта проверяет неизвестную операцию в запросе; коды для произвольных неизвестных HTTP-путей этим выводом не утверждаются. Источники: [OpenAPI](api/openapi.yaml), `components.schemas.BookingInput`, `components.schemas.Error`, `paths./bookings.post.responses.422`; [проверка параметров Tool](tool-contract.md#кто-проверяет-параметры), [таблица ошибок](tool-contract.md#ошибки). |
| **К4 Кривые параметры** | Нет обязательного поля, неверный тип, лишнее поле или недопустимое значение — `422` в формате `Error`; `details` указывает ошибочное поле. Для `end_at <= start_at` — `INVALID_INTERVAL`, поле `body.end_at`; начала в прошлом — `START_IN_PAST`, поле `body.start_at`. Синтаксически неверный JSON — `400 BAD_REQUEST`. Бронь не создаётся, неудачный перенос сохраняет исходную бронь. Источники: [OpenAPI](api/openapi.yaml), `BookingInput`, `BookingPatch`, `FieldError`, `Error`, ответы `400`/`422`; [контракт Tool](tool-contract.md#ошибки), [RescheduleBookingTool](tool-contract.md#reschedulebookingtool). |
| **К5 Воскрешение** | `CANCELLED` и `COMPLETED` терминальны: подтверждение или перенос возвращает `409 INVALID_STATE`, отмена `CANCELLED` — `409 ALREADY_CANCELLED`, отмена `COMPLETED` — `409 INVALID_STATE`. Прежняя запись сохраняется. Для новой встречи нужен новый `POST /bookings` и новый ключ; создаётся новый `id`. Старый ключ возвращает снимок создания прежней брони, не воскрешает её. Источники: [архитектура](architecture.md#запрещенные-переходы-и-ответ-системы); [Tool](tool-contract.md#cancelbookingtool); [OpenAPI](api/openapi.yaml), `rescheduleBooking`, `confirmBooking`, `cancelBooking`; [ADR-0001](adr/0001-persistent-idempotency.md#решение). |
| **К6 Отмена** | Автор вызывает `DELETE /bookings/{id}`: успешный ответ `200 Booking` со статусом `CANCELLED`, запись сохраняется, создаётся уведомление об отмене. Подтверждённую бронь можно отменить только до начала; после начала — `409 MEETING_STARTED`. Неподтверждённая при начале отменяется автоматически; повтор уже состоявшейся отмены — `409 ALREADY_CANCELLED`. Отмена не отзывает ранее отправленное SMS и не прерывает уже обрабатываемый сетевой запрос; это отмена брони. Источники: [OpenAPI](api/openapi.yaml), `paths./bookings/{id}.delete`; [CancelBookingTool](tool-contract.md#cancelbookingtool); [ADR-0002](adr/0002-recover-bookings-from-database.md#решение), [ADR-0003](adr/0003-sms-without-automatic-retry.md#решение). |
| **К7 Огромный вход** | **Сознательно не закрываем защитой от размера** в текущей учебной версии. Для корректного входа в 1000 раз больше обычного не обещаем отказ `413`/`422`, единый ответ или завершение в определённый срок: верхние границы тела, `topic`, ключа и страницы не заданы. Это принятый риск отказа сервиса, а не успешная защита. Причины, альтернативы и обязательный пересмотр до реального размещения: [ADR-0004](adr/0004-input-size-risk.md#решение). Исходное состояние схем: [OpenAPI](api/openapi.yaml), `BookingInput.topic`, заголовок `Idempotency-Key`, параметр `limit`. |
| **К8 Чужой или несуществующий id** | Операции с бронью по чужому или несуществующему UUID возвращают одинаковый `404 NOT_FOUND` в формате `Error`; поле `path.id`, без данных чужой брони. Некорректный UUID — `422`; без аутентификации — `401`. `GET /bookings` показывает только свои записи; `GET /bookings/{id}` в контракт не входит. Ограничение вывода: при конфликте интервалов контракт отдельно раскрывает `conflicting_booking_id`; сокрытие этого идентификатора не гарантируется. Тема встречи, владелец и другие данные чужой брони в ответе конфликта не предусмотрены. Источники: [OpenAPI](api/openapi.yaml), `components.responses.Error404`, операции над `/bookings/{id}`, `paths./bookings.get`; [Tool](tool-contract.md#ошибки). |
| **К9 Перезапуск сервера** | `running` к брони неприменим, но восстановление активных броней необходимо. Из БД сохраняются прежний `id` и данные: просроченная `PENDING_CONFIRMATION` → `CANCELLED`; `CONFIRMED` с прошедшим концом → `COMPLETED`, иначе остаётся `CONFIRMED`; терминальные состояния не меняются. Scheduler выполняет восстановительный проход до готовности сервиса и дальнейшие проверки; время проверяется также при обращении к брони. Сбой до commit не оставляет частично созданную бронь; после commit повтор создания восстанавливает результат по ключу. Источники: [ADR-0002](adr/0002-recover-bookings-from-database.md#решение), [ADR-0001](adr/0001-persistent-idempotency.md#решение). |
| **К10 Внешний сервис** | SmsNotifier ограничивает одно обращение 5 секундами. При молчании 30 секунд ручной `POST /notifications/{id}/retry` заканчивается `504 NOTIFICATION_TIMEOUT`; мусор, отказ или переименование обязательного поля — `502 NOTIFICATION_PROVIDER_ERROR`, формат `Error`, поле ошибки `null`. Состояние брони не меняется. Для фоновой отправки клиент не получает новый HTTP-ответ: результат пишется в запись попытки и логи. Автоматического повтора нет; при неизвестном результате ручной повтор может дублировать SMS — этот риск сознательно принят. Источники: [OpenAPI](api/openapi.yaml), `paths./notifications/{id}/retry.post`, `Error502`, `Error504`; [RetryNotificationTool](tool-contract.md#retrynotificationtool); [ADR-0003](adr/0003-sms-without-automatic-retry.md#решение). |
