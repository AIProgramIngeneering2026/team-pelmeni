# Практика 1 — заявка на проект

## Тема
### Сервис бронирования переговорных комнат

Сервис бронирования переговорных комнат — система для управления бронированием комнат внутри организации. 
Она позволяет сотрудникам находить свободные помещения, создавать бронирования на определённое время, подтверждать, отменять и переносить их.
Основная цель проекта — упростить процесс организации встреч и предотвратить ситуации, когда несколько сотрудников одновременно занимают одну и ту же комнату.

## Инженерный скелет
| # | Пункт | У нас |
|---|---|---|
| 1 | Единица работы и жизненный цикл | Бронь проходит состояния PENDING_CONFIRMATION, CONFIRMED, CANCELLED, COMPLETED. Отдельно хранится фоновое задание Job с типом действия, идентификатором брони и временем выполнения. Его состояния — PENDING, RUNNING, SUCCEEDED, FAILED, CANCELLED. Основные переходы — PENDING → RUNNING → SUCCEEDED/FAILED. Задание, утратившее актуальность до выполнения, переходит из PENDING в CANCELLED. Автоматические повторные попытки в первой версии не предусмотрены. |
| 2 | Исполнители за единым контрактом | Предусмотрены обработчики напоминания о встрече, автоматической отмены неподтверждённой брони и завершения прошедшей встречи. Все обработчики реализуют метод execute(job) и возвращают результат выполнения или описание ошибки. Перед действием обработчик проверяет актуальное состояние брони. Отдельный фоновый процесс выбирает из БД задания, время выполнения которых наступило, и передаёт их соответствующему обработчику. |
| 3 | Сетевой API | HTTP API обменивается данными в JSON. Основные операции — создание, подтверждение, отмена, перенос и просмотр броней, а также поиск свободных комнат. Для подтверждения предусмотрен POST /bookings/{id}/confirm. Конфликт интервалов возвращает 409, некорректные входные данные — 422. API документируется через OpenAPI. |
| 4 | Хранилище | Используем PostgreSQL. Основные таблицы — users, rooms, bookings, jobs, notifications. Изменения структуры БД оформляем миграциями Alembic. Для броней в статусах PENDING_CONFIRMATION и CONFIRMED на уровне БД запрещаем пересечение интервалов одной комнаты. Интервалы считаем полуоткрытыми — встреча может начинаться в момент окончания предыдущей. Создание брони и связанных заданий выполняем в одной транзакции. |
| 5 | Внешняя зависимость | Отдельный HTTP-сервис уведомлений принимает сообщения о бронированиях и записывает их в лог. Приложение обращается к нему через адаптер с ограничением времени ожидания и ограниченным числом повторных попыток при временных сбоях. Повторные запросы используют один идентификатор уведомления для защиты от дублей. Обрабатываются недоступность сервиса и некорректный ответ. Для интеграционных тестов предусмотрен fake-service с управляемыми ошибками и задержками. |
| 6 | Автотесты | Используем pytest. Проверяем основные сценарии бронирования, права доступа, некорректное время и переходы состояний. Интеграционные тесты с PostgreSQL проверяют, что при одновременных пересекающихся запросах создаётся ровно одна бронь. Для фоновых заданий проверяем выполнение, ошибку и отмену утративших актуальность действий. Ответы внешнего справочника подменяем в тестах, включая ошибки и тайм-ауты. Тесты запускаются в GitHub Actions при создании и обновлении PR. |
| 7 | Диагностика | Используем структурированные логи с уровнем события и идентификаторами запроса, брони и фонового задания. Ошибку выполнения сохраняем в записи Job. Уведомления записываем в БД и выводим через LogNotifier в лог. Endpoint /health проверяет работоспособность приложения и доступность БД. |
| 8 | Запуск одной командой | Docker Compose запускает API, фоновый обработчик, PostgreSQL и сервис уведомлений. Конфигурация читается из переменных окружения, миграции применяются при запуске. Запуск из чистого клона описан в README и выполняется командой docker compose up --build. |

## Шов для LLM
Предлагаем во втором семестре подключить LLM для обработки запросов на бронирование на естественном языке. 
Например, сотрудник сможет написать «Найди свободную переговорную завтра с 14 до 15 часов».
Модуль LLM будет преобразовывать запрос в структурированные параметры поиска и бронирования. Сервис проверит корректность времени, доступность комнаты и права пользователя. 
Перед созданием брони пользователь подтвердит предложенные параметры.
